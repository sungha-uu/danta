## 2026-07-26 활성 상단 재도달을 +10% 탄력성으로 잘못 대체

- 증상: 최근 실제 최고가가 현재가 또는 박스 하단 대비 `+10%`에 못 미치고 `+10% 도달 0일`인 미스토홀딩스가 7일 후보 3위와 추천 등급으로 표시됐다.
- 원인: 후보 자격과 최종 정렬이 `활성 하단→활성 상단 재도달`을 사용했다. 활성 상단은 최근 고가 90분위 기반이므로 상승폭이 10%보다 작을 수 있는데도, AI 점수는 재도달이 없을 때 최대 69점으로만 제한해 추천 기준 60점을 통과할 수 있었다. 사용자 검토표에도 내부 연구용 활성 구조 네 열을 그대로 노출해 핵심 판단값을 가렸다.
- 해결: 박스 하단 접촉 뒤 3거래일 내 실제 `+10%` 도달 횟수와 기간 실제 최고가의 현재가 `+10%` 도달 여부를 추천 자격과 최종 정렬의 최우선 게이트로 사용한다. 하나라도 미충족한 종목은 비추천으로 제한하고 충족 종목 뒤에만 배치한다. 사용자 표에서는 활성 구조 네 열을 제거하고 진입 기준가·`+10%` 목표가·실제 기간 최고가·`+10%` 이력을 표시한다.
- 검증: 미스토홀딩스의 현재가 44,450원, 현재가 기준 목표 48,895원과 `+10%` 도달 0일을 교차 확인하고, 재산출 뒤 추천 불가·상위 자격군 뒤 배치·실제 Pages 열 표시를 브라우저에서 확인한다.
- 재발 방지: 용어가 비슷한 통계 경계와 투자 목표를 동일 변수로 사용하지 않는다. 목표 수익 자격 테스트에는 목표 가격과 실제 원본 분봉의 순차 도달 증거를 함께 고정한다. 7·14·21일 × 후보 50개 전체를 배포 전 자동 감사하고 위반이 남으면 HTML 생성을 실패시킨다.

## 2026-07-26 기간 하단 대신 활성 위치를 사용한 아모레퍼시픽 오추천

- 증상: 아모레퍼시픽 21일 차트에서 현재가 118,000원이 기간 하단 102,700원보다 크게 높고 하단 기준 +10% 목표가 112,970원도 이미 지났는데 8위 추천으로 표시됐다.
- 원인: 화면의 박스 하단은 21일 기간 박스였지만 `현재 위치`, 후보 자격, 점수와 최종 순위는 최근 레짐으로 다시 계산한 활성 위치 15%를 사용했다. 실제 기간 위치 약 67%가 가려져 서로 다른 박스를 한 행에 섞었다.
- 해결: 후보 자격·점수·등급·순위·화면의 현재 위치를 모두 선택 기간 전체 박스 위치로 통일한다. 활성 위치와 구조 무효화는 내부 연구 산출물에만 남긴다. 하단 기준 +10% 목표가가 현재가 이하이면 이미 진입 시점을 지난 것으로 판정해 추천을 금지한다.
- 검증: 아모레퍼시픽 21일 위치가 기간 박스 기준으로 재계산되고 비추천·후순위가 되는지 확인한다. 7·14·21일 전체 READY 후보에서 표시 위치 재계산, 목표가 선후관계와 추천·순위 불변조건을 자동 감사한다.
- 재발 방지: 한 행에서 박스 경계와 위치의 기준 구간이 다르면 대시보드 생성을 실패시킨다.

## 2026-07-26 KIS 분봉 재수집 중 EGW00201

- 증상: 실제 보고서 재생성 과정에서 KIS 분봉 API가 `EGW00201 초당 거래건수 초과`를 반환해 백필 단계가 중단됐다.
- 원인: 이미 저장된 7일 분봉이 있는 상태에서도 불완전 종목의 누락분을 채우려는 요청이 KIS 호출 제한에 걸렸다.
- 해결: 보고서 산출과 외부 백필을 분리하고 `danta intraday-report --skip-backfill`을 추가했다. 이 옵션은 KRX 기준일과 저장된 1분봉만 읽어 계산하며 KIS 분봉 API를 호출하지 않는다.
- 검증: 저장 분봉 기반 보고서 생성, 전체 테스트, 정적 대시보드 렌더링과 Pages 브라우저 검증을 수행한다.
- 재발 방지: 단순 즉시 재시도를 해결로 간주하지 않는다. 백필은 제한 속도·체크포인트를 따르고, 데이터가 충분한 재계산은 외부 시세 호출과 분리한다.

## 2026-07-26 무효화된 활성 박스의 과대평가

- 증상: 첫 Pages 브라우저 검증에서 현재가가 활성 하단권 아래인 일부 종목이 음수 위치값으로 높은 하단 점수를 받고, 해결 표본 1회의 관측 재도달률 100%로 적극 추천될 수 있었다.
- 원인: 활성 위치 하단 가산에는 하한이 있었지만 현재가와 구조 무효화 가격의 선후관계를 자격 게이트에서 검사하지 않았고, `LOW` 신뢰도에 적극 추천 상한이 없었다.
- 해결: 현재가가 활성 구조 무효화선 아래면 추천 자격을 차단하고 정량 위치 가산을 20%로 감쇠했다. 에이전트 점수는 비추천 구간으로 제한하고, `LOW` 신뢰도는 적극 추천으로 승격하지 않게 했다. 화면 명칭도 `후향 관측 재도달률`로 명확히 했다.
- 검증: 무효화 종목 추천 0개, `LOW` 신뢰 적극 추천 0개를 산출물에서 확인했다. 전체 테스트 68개, Ruff, mypy를 통과하고 Pages의 7·14·21일 각 50행과 차트 팝업을 실제 브라우저에서 확인했다.
- 재발 방지: 낮은 위치를 기회로 가산하기 전에 활성 구조 유효성을 먼저 검사하고, 비율에는 항상 해결 표본과 신뢰도를 함께 노출한다.

## 1. 필수 운영 규칙

문제가 발생하면 임시 우회만 하고 끝내지 않는다. 다음 순서로 처리한다.

1. 피해 확산을 막는다. 주문 관련 문제면 신규매수를 먼저 차단하되 보호 매도는 유지한다.
2. 비밀정보를 노출하지 않고 증상, 환경, 시각, 오류코드, 상관 ID를 수집한다.
3. 재현 가능한 최소 사례를 만든다.
4. 직접 원인과 기여 요인을 구분한다.
5. 코드·설정·운영 절차 중 올바른 위치에서 수정한다.
6. 정상·경계·재발 시나리오 테스트로 해결을 검증한다.
7. 이 문서에 원인, 해결, 검증, 재발방지 조치를 남긴다.
8. 관련 기준 문서와 코드가 어긋났다면 같은 변경에서 갱신한다.

다음 중 하나라도 해당하면 반드시 기록한다.

- 주문·체결·잔고·손절·익절에 영향을 준 문제
- 외부 API의 실제 동작이 문서 또는 예상과 달랐던 문제
- 같은 원인이 반복될 가능성이 있는 문제
- 해결을 위해 코드·설정·운영절차를 변경한 문제
- 데이터 누락·오염·미래정보 누수 가능성이 있었던 문제
- 비밀정보·권한·대시보드 제어 경계 문제

단순 오타처럼 재발 가치가 없는 사항은 기록하지 않는다.

```markdown

- 상태: OPEN | MITIGATED | RESOLVED | MONITORING
- 심각도: S1 | S2 | S3 | S4
- 환경: local | paper | small-live | production
- 최초 발생·해결 시각:
- 영향:
- 탐지:

### 증상과 재현

### 기여 요인

```

심각도:

- `S1`: 오주문, 보호 매도 불능, 비밀 노출, 계좌 상태 훼손
- `S2`: 신규주문 중단, 잔고 불일치, 실시간 감시 장시간 중단
- `S3`: 일부 데이터·알림·배치 실패, 안전 차단으로 거래 영향 제한
- `S4`: 개발 편의·문서·비핵심 성능 문제

기록에는 App Key, 토큰, 전체 계좌번호, 이메일 비밀번호, 원시 인증 응답을 넣지 않는다.

## 3. 해결 완료 기준

`RESOLVED`는 다음이 모두 충족될 때만 사용한다.

- 원인이 증거로 설명됨
- 수정 코드 또는 운영 절차가 존재함
- 재현 테스트와 회귀 테스트가 통과함
- 주문·위험 영향이 확인됨
- 관련 기준 문서가 갱신됨
- 남은 위험과 후속 작업이 명시됨

원인을 모른 채 재시도로만 정상화되면 `MONITORING`이지 `RESOLVED`가 아니다.

## 4. 누적 기록

### TS-20260726-001 KIS 모의 REST 호출 제한과 토큰 재발급 충돌

- 상태: RESOLVED
- 심각도: S3
- 환경: paper
- 발생·해결: 2026-07-26
- 영향: `provider-doctor` 잔고 조회 실패, 주문 호출은 없었음
- 탐지: live doctor의 HTTP 실패와 KIS 오류코드 `EGW00201`

#### 증상과 재현

KIS 모의계좌 live doctor에서 토큰과 현재가 요청 뒤 잔고 조회가 실패했다. 진단을 즉시 다시 실행했을 때는 토큰 발급도 HTTP 403으로 거부됐지만 WebSocket 접속키는 발급됐다.

#### 직접 원인

- 모의 REST 현재가와 잔고 요청을 허용 간격 없이 연속 호출해 `EGW00201` 초당 거래건수 초과가 발생했다.
- 프로세스 종료 때 접근토큰을 잃어 진단 재실행마다 토큰을 새로 발급하려 했다.

#### 기여 요인

- 초기 클라이언트에 공급자별 중앙 호출 제한기가 없었다.
- HTTP 오류 응답에서 KIS의 안전한 오류코드·메시지를 보존하지 않아 첫 원인 식별이 늦었다.

#### 즉시 완화

주문을 호출하지 않은 상태에서 진단을 중단하고, 응답의 HTTP 상태와 KIS 오류코드만 출력하도록 분리 진단했다.

#### 영구 해결

- KIS 모의 REST 요청을 `asyncio.Lock`으로 직렬화했다.
- 실측된 모의환경에 최소 1.1초 요청 간격을 적용했다.
- 접근토큰을 Git 제외 비밀 경로에 만료시각과 함께 원자적으로 캐시했다.
- 오류 본문 전체 대신 `msg_cd`, `msg1`만 안전하게 노출하도록 수정했다.
- live doctor 결과를 비민감 capability snapshot으로 저장했다.

1.1초는 2026-07-26 모의환경에서 확인된 현재 완화값이며 영구적인 공식 한도로 간주하지 않는다. `provider-doctor`와 공식 공지에 따라 변경한다.

#### 검증

- Ruff 통과
- Mypy 통과
- 테스트 22개 통과
- 모의 토큰, 삼성전자 현재가, 잔고, WebSocket 접속키 live doctor 전부 통과
- 모의계좌 보유종목 0개 확인
- 주문 호출 0건

#### 재발 방지와 후속 작업

- 모든 KIS REST 호출은 동일한 중앙 제한기를 통과시킨다.
- `EGW00201` 발생 시 즉시 반복하지 않고 지수 백오프와 계측을 적용한다.
- 토큰은 프로세스별로 새로 발급하지 않고 공유 캐시·단일 잠금을 사용한다.
- 향후 다중 프로세스에서는 프로세스 간 분산 제한기와 잠금으로 승격한다.

#### 관련 코드·문서·버전

- `src/danta/adapters/kis/client.py`
- `src/danta/services/provider_doctor.py`
- `data/provider_capability_snapshot.json`
- `DOCS/DEVELOPMENT.md`
- Danta `0.1.0`

### TS-20260726-002 승인문 복사 성공이 화면에 표시되지 않음

- 상태: RESOLVED
- 심각도: S4
- 환경: 정적 GitHub Pages 대시보드
- 발생·해결: 2026-07-26
- 영향: 승인문은 클립보드에 복사됐지만 사용자가 성공 여부를 즉시 확인하기 어려웠으며 주문 호출 영향은 없음

#### 원인

선택창을 압축하면서 복사 결과 문구를 스크린리더용 숨김 상태 메시지로만 남겼고, 시각적 성공·실패 표시를 별도로 제공하지 않았다.

#### 해결

- 클릭 즉시 클립보드 쓰기를 요청한다.
- 버튼을 약 1초간 회전 진행 상태로 두어 중복 클릭을 차단한다.
- 성공 시 체크 아이콘과 `승인문 복사 완료` 팝업을 표시한다.
- 실패 시 브라우저 클립보드 권한 확인 팝업을 표시한다.
- 숨김 접근성 상태 메시지는 함께 유지한다.

#### 검증과 재발 방지

- 유효한 선택에서 진행 상태 중 버튼 비활성화를 확인한다.
- 1초 후 성공 팝업과 버튼 원상복구를 확인한다.
- 정적 HTML 테스트에서 진행 표시·팝업·대기시간을 검사한다.
- 향후 주요 아이콘 작업은 성공·실패·진행 상태를 시각·접근성 양쪽에서 제공한다.

### TS-20260726-003 SMTP 테스트의 MIME 원문 비교 실패

- 상태: RESOLVED
- 심각도: S4
- 환경: 로컬 단위 테스트
- 발생·해결: 2026-07-26

- 증상: 후보표 정렬·기간 전환처럼 본문을 다시 렌더링한 뒤 가격 흐름 미니차트를 눌러도 60분봉 팝업이 열리지 않았다.
- 원인: 동적으로 교체되는 각 미니차트 버튼에 렌더링 때마다 클릭 이벤트를 다시 연결하는 구조여서 재렌더링 생명주기와 이벤트 연결이 분리될 수 있었다.
- 해결: 교체되지 않는 `rankingBody`에 클릭 이벤트를 한 번만 연결하고 `.spark-button`을 식별하는 이벤트 위임 방식으로 변경했다.
- 검증: 정렬·기간 전환·순위 초기화 뒤 미니차트를 눌러 팝업 표시, 종가 셀 수, 숨긴 상세값 부재를 실제 브라우저에서 확인한다.
- 재발 방지: 동적 표 행의 버튼 이벤트는 행별 재연결보다 안정적인 상위 컨테이너 이벤트 위임을 기본으로 하고 Pages 배포 전 재렌더링 뒤 팝업 클릭을 필수 점검한다.

## 2026-07-28 진입·청산 actor 결정 타입 충돌

- 증상: 전체 테스트는 통과했지만 strict mypy가 진입 결정 변수에 청산 결정을 재대입한
  두 지점을 거부했다.
- 원인: 서로 다른 DTO를 한 분기 함수 안에서 같은 지역 변수명으로 사용해 정적 타입이
  첫 분기의 `EntryDecision`으로 고정됐다.
- 해결: `entry_decision`, `exit_decision`을 분리하고 전체 strict mypy를 재실행했다.
- 검증: strict mypy 56개 소스 파일 오류 0건.
- 재발 방지: 주문 결정 DTO는 종류별 이름을 사용하고 합집합으로 암묵 재사용하지 않는다.

## 2026-07-28 WebSocket 장애가 손절 감시를 함께 끊을 위험

- 증상: 최초 실행 조립은 체결 WebSocket 이벤트가 들어올 때만 위험 엔진을 평가했다.
- 원인: 분석 신호와 불변 손절 트리거가 같은 데이터 경로에 의존했다.
- 해결: 보유 포지션마다 KIS REST 현재가를 별도로 조회하는
  `process_watchdog_price` 경로를 추가했다. 이 경로는 익절 정책 승인 여부와 무관하게
  평균 체결가 대비 -7%에서 같은 최우선 시장가 매도 의도를 만든다.
- 검증: WebSocket 이벤트 없이 REST 가격만으로 `HARD_STOP_MINUS_7` 의도가 생성되는
  회귀 테스트를 추가했다.
- 재발 방지: 신규 데이터 기능을 추가할 때 보호 경로와 장애 도메인을 공유하는지
  `QUALITY_AND_VALIDATION.md`에서 별도 점검한다.

## 2026-07-28 코드 완성과 모의 운용 승격 혼동 방지

- 증상: 모든 모듈 구현 요구가 실제 주문 장애 검증 없이 “실전 가능” 선언으로 이어질 수 있었다.
- 원인: 기능 존재와 운영 증거를 같은 완료 상태로 표현했다.
- 해결: `assure` 기계 판독 보고서와 `paper_order_execution_enabled`,
  `paper-trade --execute`의 이중 게이트를 추가했다. DB 마이그레이션, 정책 승인,
  비밀 설정과 모의 주문 플래그 중 하나라도 없으면 신규 모의매수를 차단한다.
- 검증: 기본 설정에서는 주문이 잠기며 승인문 검증만 가능하다.
- 재발 방지: 실제 KIS 모의 주문·부분체결·재시작·장애 증거 전에는
  `PAPER_READY`, `LIVE_READY` 표현을 사용하지 않는다.
